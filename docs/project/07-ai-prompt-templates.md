# 7. Prompt Template สำหรับ AI: ออกแบบและสร้างระบบ

Template ชุดนี้ใช้สั่ง AI ให้ทำงานกับโครงการนี้ โดยให้ผลลัพธ์เข้ากับโครงสร้างและกติกาที่มีอยู่
ใช้ได้กับ AI ที่อ่านไฟล์ใน repo ได้ (เช่น Claude Code) ถ้าใช้กับ AI ที่อ่านไฟล์ไม่ได้ ให้แนบไฟล์ที่ template อ้างถึงไปด้วย

Template เหล่านี้เข้ามาแทน `docs/prompts/AI_PROMPT_BACKEND.md` และ `AI_PROMPT_FRONTEND.md` สำหรับงานประจำ
สองไฟล์นั้นเป็นภาพรวมระดับสูง ส่วนชุดนี้ลงรายละเอียดของงานแต่ละประเภท

## วิธีใช้

1. เริ่มด้วย **บล็อกบริบท** (หัวข้อ 1) เสมอ
2. ต่อด้วย template ของงานที่ต้องการ แล้วแทนค่าใน `{{...}}`
3. ระบุสิ่งที่ **ไม่** ต้องการให้ทำ ถ้ามี
4. ตรวจผลตามรายการในหัวข้อ 11 ก่อนรับงาน

หลักที่ทำให้ได้ผลดี: บอกเป้าหมายและเหตุผล ไม่ใช่แค่วิธีทำ, ชี้ไปที่ไฟล์จริงแทนการอธิบายซ้ำ, ระบุวิธีพิสูจน์ว่างานเสร็จ, และให้ AI ถามเมื่อเจอการตัดสินใจเชิงธุรกิจ

## 1. บล็อกบริบท (ใส่ทุกครั้ง)

```text
คุณกำลังทำงานในโครงการ Senic POS: ระบบขายหน้าร้านแบบ SaaS สำหรับหลายร้านค้า

อ่านก่อนเริ่ม:
- docs/API_REFERENCE.md         สัญญา API (แหล่งอ้างอิงหลักของ endpoint)
- docs/project/03-system-blueprint.md                 โครงสร้างระบบ
- docs/project/04-technical-design-and-specifications.md   กติกาและข้อกำหนด
- frontend/README.md และ backend/README.md            วิธีรันและข้อตกลงในโค้ด

สแต็ก:
- Backend: .NET 10, ASP.NET Core, EF Core 10, PostgreSQL, Clean Architecture
  (API → Application → Domain, Infrastructure)
- Frontend: React 19, TypeScript, Vite, Tailwind CSS 4, TanStack Query, Zustand,
  React Hook Form + Zod, i18next (ไทย/อังกฤษ)

กติกาที่ห้ามละเมิด:
1. รหัสร้าน (tenant) อ่านจาก access token เท่านั้น ห้ามรับจาก URL หรือ body
   ข้อมูลของร้านต้องมี query filter ใน ApplicationDbContext
2. ถ้าเปลี่ยน endpoint ต้องแก้ docs/API_REFERENCE.md, backend, frontend
   และ API จำลอง (frontend/src/mocks) ในงานเดียวกัน
3. ทุกการเปลี่ยนแปลงต้องมี test และคำสั่งต่อไปนี้ต้องผ่าน:
   backend: dotnet test
   frontend: npm run lint && npm run format:check && npm test && npm run build
4. Frontend: เรียก API ผ่าน api ใน src/lib/api.ts เท่านั้น, ข้อความบนหน้าจอ
   ต้องอยู่ใน th.json และ en.json, ใช้ design token ไม่ใช้สีจาก palette ตรง ๆ,
   ห้ามใช้ enum ของ TypeScript
5. ห้ามใส่ความลับลงในโค้ดหรือเอกสาร
6. ถ้าเจอการตัดสินใจเชิงธุรกิจ (เช่น สูตรคำนวณเงิน สิทธิ์ของบทบาท) ให้หยุดและถาม
   พร้อมเสนอทางเลือก อย่าตัดสินใจเอง

วิธีรายงานผล: บอกว่าทำอะไร, ตรวจด้วยอะไรและผลเป็นอย่างไร, อะไรที่ยังไม่ได้ตรวจ
และอะไรที่ต่างจากที่ขอ
```

## 2. ออกแบบระบบหรือฟีเจอร์ใหม่ (ยังไม่เขียนโค้ด)

```text
{{บล็อกบริบท}}

งาน: ออกแบบ {{ชื่อฟีเจอร์}} โดยยังไม่เขียนโค้ด

ปัญหาที่ต้องแก้: {{ใครเจอปัญหาอะไร ตอนไหน}}
ผลลัพธ์ที่ต้องการ: {{ผู้ใช้ทำอะไรได้เมื่อเสร็จ}}
ข้อจำกัด: {{เช่น ต้องทำงานออฟไลน์, ต้องไม่เปลี่ยน endpoint เดิม}}
นอกขอบเขต: {{สิ่งที่ไม่ต้องทำ}}

สิ่งที่ต้องส่ง:
1. สรุปแนวทางที่แนะนำใน 3–5 ประโยค และเหตุผลที่เลือก
2. ทางเลือกอื่นที่พิจารณา และเหตุที่ไม่เลือก
3. การเปลี่ยนแปลงของสัญญา API: endpoint, บทบาท, request/response, status code
4. การเปลี่ยนแปลงของข้อมูล: entity, คอลัมน์, index, migration
5. ผลกระทบต่อการแยกข้อมูลตามร้าน สิทธิ์ การทำงานออฟไลน์ และการแจ้งเตือน
6. รายการไฟล์ที่จะสร้างหรือแก้ แยก backend และ frontend
7. แผน test: กรณีที่ต้องครอบคลุม
8. คำถามและการตัดสินใจที่ต้องให้คนตอบ

อย่าเดาข้อกำหนดทางธุรกิจที่ไม่ได้ให้ไว้ ให้ระบุเป็นคำถามในข้อ 8
```


## 7. เขียนหรือเสริม test

```text
{{บล็อกบริบท}}

งาน: เพิ่ม test ให้ {{ส่วนของระบบ}}

พฤติกรรมที่ต้องยืนยัน: {{รายการกติกา}}

แนวทาง:
- ตั้งชื่อ test ตามพฤติกรรมที่ผู้ใช้เห็น ไม่ใช่ตามชื่อฟังก์ชัน
- Backend: ใช้ ApiFactory ใน SenicPosSaaS.Tests/Api เพื่อทดสอบผ่าน HTTP
  แต่ละ test สร้างข้อมูลของตัวเอง
- Frontend: ใช้ renderApp ใน src/test/render-app.tsx กับ API จำลอง
  ใช้ global ของ Vitest ไม่ import จาก 'vitest'
- หลังเขียน ให้พิสูจน์ว่า test จับข้อผิดพลาดได้จริง โดยทำให้โค้ดผิดชั่วคราว
  แล้วยืนยันว่า test ล้ม จากนั้นคืนโค้ด

รายงานด้วยว่ามีพฤติกรรมใดที่ test ไม่ได้ครอบคลุม
```

## 8. ทบทวนโค้ด

```text
{{บล็อกบริบท}}

งาน: ทบทวนการเปลี่ยนแปลงใน {{branch / pull request / รายการไฟล์}}

ตรวจตามลำดับความสำคัญ:
1. ข้อมูลรั่วข้ามร้านได้หรือไม่: มี entity ใหม่ที่ไม่มี query filter,
   มีการรับ tenantId จาก client, หรือมี IgnoreQueryFilters ที่ไม่กรองร้านเองหรือไม่
2. สิทธิ์: endpoint ใหม่กำหนดบทบาทตรงกับสัญญาหรือไม่
3. ความถูกต้องของเงินและสต็อก: การปัดเศษ, การบันทึกหลายตารางสำเร็จหรือล้มเหลวพร้อมกัน
4. ความลับ: มีค่าลับในโค้ด log หรือข้อความ error หรือไม่
5. สัญญา API: เอกสาร backend frontend และ API จำลองตรงกันหรือไม่
6. การทำงานออฟไลน์: การเปลี่ยนแปลงกระทบการส่งซ้ำของบิลหรือไม่
7. Test: ครอบคลุมกรณีปฏิเสธ ไม่ใช่แค่กรณีปกติ

รายงานเฉพาะปัญหาที่ยืนยันได้ พร้อมไฟล์ บรรทัด และสถานการณ์ที่ทำให้เกิดปัญหา
แยก "ต้องแก้" ออกจาก "ข้อเสนอแนะ"
```

## 9. เปลี่ยนโครงสร้างข้อมูล

```text
{{บล็อกบริบท}}

งาน: {{เพิ่ม/เปลี่ยน/ลบ}} {{ตาราง หรือ คอลัมน์}}
เหตุผล: {{...}}
ข้อมูลที่มีอยู่แล้วใน production: {{มี/ไม่มี และต้องทำอย่างไรกับมัน}}

ข้อกำหนด:
- สร้าง migration ด้วย dotnet ef migrations add {{ชื่อ}} --project SenicPosSaaS.Infrastructure
- Migration ต้องรันได้บนฐานข้อมูลที่มีข้อมูลอยู่แล้วโดยไม่เสียข้อมูล
- ถ้าเป็นการเปลี่ยนที่ไม่เข้ากันกับโค้ดเวอร์ชันก่อน ให้เสนอการทำเป็นหลายขั้น
- อธิบายว่าถ้าต้อง rollback เวอร์ชันของแอป ฐานข้อมูลหลัง migration ยังใช้กับเวอร์ชันเก่าได้หรือไม่
```

## 11. รายการตรวจก่อนรับงานจาก AI

- [ ] รายงานบอกชัดว่าตรวจด้วยอะไร และอะไรที่ยังไม่ได้ตรวจ
- [ ] `dotnet test` และชุดคำสั่งของ frontend ผ่าน โดยรันเองอีกครั้ง
- [ ] ไม่มีการรับรหัสร้านจาก client และ entity ใหม่มี query filter
- [ ] `docs/API_REFERENCE.md` ตรงกับโค้ดสองฝั่ง
- [ ] ไม่มีความลับในโค้ด เอกสาร หรือ log
- [ ] ข้อความบนหน้าจอมีทั้งไทยและอังกฤษ
- [ ] เปิดหน้าจอที่เปลี่ยนในเบราว์เซอร์จริงแล้ว
- [ ] การตัดสินใจเชิงธุรกิจที่ AI ทำแทน (ถ้ามี) ถูกทบทวนโดยคน

# 6. ข้อเสนอแนะสแต็กเทคโนโลยี (Tech Stack Recommendation)

## สรุป

**คงสแต็กปัจจุบันไว้ทั้งหมด** ไม่มีเทคโนโลยีใดที่เป็นอุปสรรคต่อแผนใน [แผนแม่บท](02-master-plan.md)
สิ่งที่ควรทำคือ **เพิ่ม** ส่วนที่ขาดสำหรับการใช้งานจริง ตามลำดับความจำเป็น ไม่ใช่เปลี่ยนของเดิม

ข้อเสนอในเอกสารนี้มาจากความต้องการของระบบตามที่วิเคราะห์ไว้ ยังไม่ได้ทดลองใช้เทคโนโลยีที่เสนอเพิ่มกับโครงการนี้ และไม่ได้เปรียบเทียบราคา
ก่อนตัดสินใจเลือกผลิตภัณฑ์เจาะจง ควรตรวจเอกสารและราคาปัจจุบันของแต่ละตัว

## 2. สิ่งที่ควรเพิ่ม

### สำหรับ Milestone 1: พร้อมใช้งานจริง

| ความต้องการ | ข้อเสนอ | หมายเหตุ |
| --- | --- | --- |
| HTTPS | Reverse proxy ที่ออกใบรับรองอัตโนมัติ เช่น Caddy, Traefik หรือ Nginx Proxy Manager | จำเป็น: login, push และการติดตั้งแอปต้องใช้ HTTPS |
| จำกัดการ login | Rate limiting ที่มากับ ASP.NET Core และการล็อกบัญชีชั่วคราว | ไม่ต้องเพิ่ม library |
| สำรองฐานข้อมูล | งานตามเวลาที่รัน `pg_dump` แล้วส่งไปเก็บนอก server | เริ่มจากวิธีง่ายก่อน |
| เฝ้าระวัง | บริการตรวจ `/health` จากภายนอกพร้อมแจ้งเตือน | |
| รวม log | ส่ง log ของ container ไปที่เก็บกลางด้วย Serilog sink | |
| ความถูกต้องของสต็อก | Optimistic concurrency ของ EF Core (คอลัมน์เวอร์ชันของ PostgreSQL) | ไม่ต้องเพิ่ม library |
| End-to-end test | Playwright | ครอบคลุมช่องว่างเรื่องการตรวจในเบราว์เซอร์จริง |
| Test กับฐานข้อมูลจริง | Testcontainers สำหรับ PostgreSQL | ฐานข้อมูลใน memory ไม่บังคับ unique index และพฤติกรรมของ SQL |

### สำหรับ Milestone 2: ธุรกิจครบวงจร

## 3. สิ่งที่ไม่แนะนำในตอนนี้

| แนวคิด | เหตุผลที่ยังไม่ควรทำ |
| --- | --- |
| แยกเป็น microservices | ระบบมีโค้ด backend ประมาณ 3,900 บรรทัดและทีมเล็ก การแยกเพิ่มงานดูแลโดยไม่แก้ปัญหาที่มีอยู่จริง |
| ย้ายไป Kubernetes | Docker Compose บน server เดียวเพียงพอจนกว่าจะต้องรันหลาย instance |
| แยกฐานข้อมูลต่อร้าน | การกรองด้วย `TenantId` ทำงานได้และมี test กำกับ การแยกฐานข้อมูลเพิ่มงาน migration และการสำรองตามจำนวนร้าน |
| GraphQL | REST ตามสัญญาปัจจุบันครอบคลุมความต้องการ และมี client เดียว |
| เปลี่ยน framework ของ frontend อีกครั้ง | เพิ่งย้ายจาก Angular มา React เสร็จ ไม่มีเหตุผลทางเทคนิค |
| แอป native บนมือถือ | PWA ครอบคลุมการติดตั้ง ออฟไลน์ และ push แล้ว ควรรอผลการใช้งานจริงก่อน |
| อัปเกรดเป็น .NET 11 | .NET 10 เป็นรุ่น LTS ควรอยู่บนรุ่น LTS สำหรับระบบที่ให้บริการลูกค้า |

## 4. นโยบายเวอร์ชันที่เสนอ

- **Backend:** อยู่บน .NET รุ่น LTS และตรึง package ของ Microsoft ที่สาย 10.x ระวังคำสั่ง `dotnet add package` ที่ไม่ระบุเวอร์ชัน เพราะจะได้รุ่น 11 ซึ่งใช้กับ `net10.0` ไม่ได้
- **Frontend:** Node รุ่น LTS (CI และ image ใช้ Node 24) และอัปเดต dependency เป็นรอบ เช่น เดือนละครั้ง พร้อมรัน test
- **ความปลอดภัย:** รัน `npm audit` และตรวจ package ของ .NET ใน CI และแก้ช่องโหว่ระดับ high ขึ้นไปก่อน deploy
- **Image ฐาน:** ดึงใหม่ทุกครั้งที่ build ใน CI เพื่อให้ได้ patch ล่าสุด

## 5. ทางเลือกที่พิจารณา

| ประเด็น | ทางที่เลือก | ทางเลือกอื่น | เหตุที่ไม่เลือก |
| --- | --- | --- | --- |
| State ของ frontend | TanStack Query + Zustand | Redux Toolkit | ข้อมูลส่วนใหญ่มาจาก server และ state ในเครื่องมีน้อย |
| ข้อมูลออฟไลน์ | IndexedDB ที่จัดการเอง | Cache API ของ service worker | แยกตามร้านไม่ได้ และค้นหาคำใหม่ตอนออฟไลน์ไม่ได้ |
| Real-time | SignalR | Server-Sent Events, WebSocket ตรง | มากับ ASP.NET Core และจัดการการเชื่อมต่อใหม่ให้ |
| ที่เก็บ refresh token | Cookie HttpOnly | localStorage | ป้องกันการขโมยผ่าน script ที่ถูกฝัง |
| เครื่องมือ deploy | Portainer + Compose | Kubernetes, PaaS | ตรงกับขนาดปัจจุบันและความต้องการของเจ้าของโครงการ |

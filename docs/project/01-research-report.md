# 1. รายงานการวิจัยและวิเคราะห์โครงการ

## สรุปสำหรับผู้บริหาร

Senic POS เป็นระบบขายหน้าร้านแบบ SaaS สำหรับหลายร้านค้า (multi-tenant) ประกอบด้วย backend (.NET 10 + PostgreSQL) และ frontend (React 19 แบบ PWA)
แกนหลักของระบบทำงานได้จริงแล้ว: login ตามบทบาท, ขายหน้าร้านรวมถึงตอนออฟไลน์, จัดการสินค้า, ลูกค้าและแต้มสะสม, dashboard, แจ้งเตือนแบบ real-time และ push, และมี pipeline สำหรับ deploy

ข้อสรุป 3 ข้อ:

1. **พื้นฐานทางเทคนิคแข็งแรง** การแยกข้อมูลระหว่างร้านทำที่ระดับฐานข้อมูล มี test อัตโนมัติ 139 ข้อ และ stack production รันผ่านบน PostgreSQL จริงในเครื่อง
2. **ยังไม่พร้อมให้ร้านค้าจริงใช้** สิ่งที่ขาดเป็นเรื่องการใช้งานจริงมากกว่าฟีเจอร์: ยังไม่มีการจัดการผู้ใช้ ไม่มีการสำรองข้อมูล ไม่มีการเฝ้าระวังระบบ และหน้าจอยังไม่เคยถูกตรวจในเบราว์เซอร์จริง
3. **มีการตัดสินใจเชิงธุรกิจค้างอยู่ 4 เรื่อง** ที่กระทบโค้ดโดยตรง (ดูหัวข้อ 8)

## 1. ขอบเขตและวิธีวิเคราะห์

รายงานนี้วิเคราะห์จากสภาพจริงของ repository ณ วันที่ 27 พฤศจิกายน 2026:

- อ่านโค้ดทั้ง backend และ frontend
- ผลของ test อัตโนมัติ: backend 68 ข้อ, frontend 54 ข้อ, script deploy 17 ข้อ
- การรัน stack production (web, api, postgres) ในเครื่องด้วย Docker และ smoke test 27 ข้อผ่าน nginx

**สิ่งที่รายงานนี้ไม่ได้ทำ:** ไม่ได้สำรวจตลาด คู่แข่ง ราคา หรือสัมภาษณ์ผู้ใช้ และไม่ได้วัดประสิทธิภาพภายใต้ภาระงาน
ข้อความใดในชุดเอกสารนี้ที่เกี่ยวกับตลาดหรือผู้ใช้จึงเป็นสมมติฐานที่ต้องตรวจสอบ

## 2. ภาพรวมโครงการ

| หัวข้อ | รายละเอียด |
| --- | --- |
| ผลิตภัณฑ์ | ระบบขายหน้าร้าน (POS) ให้บริการแบบสมัครสมาชิกรายเดือน |
| ผู้ใช้ | เจ้าของร้าน ผู้ดูแล แคชเชียร์ และผู้ดูรายงาน ของร้านค้าปลีกและร้านอาหาร |
| รูปแบบ | Web application ที่ติดตั้งเป็นแอปได้ (PWA) ใช้บนคอมพิวเตอร์ แท็บเล็ต และมือถือ |
| ภาษา | ไทยและอังกฤษ |
| ขนาดโค้ด | Backend ประมาณ 3,900 บรรทัด (ไม่รวม test และ migration), frontend ประมาณ 5,000 บรรทัด, test รวมประมาณ 2,800 บรรทัด |
| API | 32 endpoint ใน 8 controller และ SignalR hub 1 ตัว |
| ข้อมูล | 9 entity บน PostgreSQL 16 |

### ประวัติโดยย่อ

โครงการเริ่มจาก frontend Angular 20 และ backend .NET 9 ที่ยังเชื่อมกันไม่ได้: backend ไม่มีระบบ login และรับรหัสร้านจาก URL
ส่วน frontend เรียก endpoint ที่ไม่มีอยู่จริง การปรับระบบที่ผ่านมาทำ 8 เรื่อง:

1. กำหนดสัญญา API กลาง ([docs/API_REFERENCE.md](../API_REFERENCE.md))
2. เขียน frontend ใหม่ด้วย React แล้วลบ Angular ออก
3. ทำ backend ให้ตรงสัญญา: login, สิทธิ์, การแยกข้อมูลตามร้าน
4. เพิ่มการขายแบบออฟไลน์และ PWA
5. เพิ่มการแจ้งเตือนแบบ real-time, push notification และการส่งออก CSV
6. อัปเกรดเป็น .NET 10
7. สร้าง CI/CD ด้วย GitHub Actions และ Portainer
8. เพิ่มการสร้างผู้ใช้คนแรกและการ migrate อัตโนมัติสำหรับ production

## 4. สถาปัตยกรรมโดยสรุป

- **Backend** ใช้ Clean Architecture 4 ชั้น: API, Application, Domain, Infrastructure
- **Frontend** แบ่งตามฟีเจอร์ ใช้ TanStack Query สำหรับข้อมูลจาก server และ Zustand สำหรับ state ในเครื่อง
- **การแยกข้อมูลตามร้าน** รหัสร้านอ่านจาก access token เท่านั้น และทุก query ถูกกรองด้วย global query filter ของ EF Core
- **การ deploy** เป็น 3 container: nginx (เสิร์ฟ frontend และส่งต่อ `/api`), API, PostgreSQL

รายละเอียดและแผนภาพอยู่ใน [พิมพ์เขียวสถาปัตยกรรมระบบ](03-system-blueprint.md)

## 7. จุดแข็ง

- **การแยกข้อมูลระหว่างร้านทำหลายชั้น** ทั้งที่ token, query filter และการตรวจตอนบันทึก
- **การขายไม่ซ้ำ** ทุกบิลมี `clientOrderId` การส่งซ้ำจึงไม่สร้างบิลใหม่ ซึ่งเป็นฐานของการขายออฟไลน์
- **ความปลอดภัยของ session** access token อยู่ใน memory, refresh token อยู่ใน cookie แบบ HttpOnly และใช้ได้ครั้งเดียว
- **สัญญา API เป็นเอกสารเดียว** และมี test กำกับทั้งสองฝั่ง
- **Deploy ทำซ้ำได้** stack เดียวกันรันได้ทั้งในเครื่องและ production และ pipeline ตรวจว่าเวอร์ชันใหม่ขึ้นจริง

### หนี้ทางเทคนิคและเอกสาร

- เอกสารเก่า 5 ไฟล์ยังอธิบายระบบเดิม (รายชื่ออยู่ใน [README](README.md))

- `npm audit` รายงานช่องโหว่ระดับ moderate 4 รายการในเครื่องมือ build
- Log ของ API ออก console ซ้ำสองครั้งจากการตั้งค่า Serilog ซ้อนกัน

## 9. การตัดสินใจที่ค้างอยู่

1. **สูตรภาษี**: ตอนนี้คิด 7% จากยอดสินค้าก่อนหักส่วนลดท้ายบิล ต้องยืนยันว่าถูกต้อง และราคาสินค้ารวม VAT แล้วหรือยัง
2. **การเข้าแอปตอนออฟไลน์**: ถ้า reload ขณะติดต่อ server ไม่ได้ แอปเข้าเป็นผู้ใช้คนล่าสุดโดยไม่ถามรหัสผ่านเพื่อให้ขายต่อได้ ต้องยืนยันว่ายอมรับได้สำหรับเครื่องที่ใช้ร่วมกัน
3. **สต็อกติดลบสำหรับบิลออฟไลน์**: บิลออฟไลน์ที่สต็อกจริงไม่พอจะถูกปฏิเสธและค้างให้คนจัดการ ทั้งที่ขายไปแล้ว
4. **ผู้ดูแลแพลตฟอร์ม**: ยังไม่มีตัวตนของผู้ให้บริการที่แยกจากผู้ใช้ของร้าน

## 10. ข้อเสนอแนะ

1. ทำ "ความพร้อมใช้งานจริง" ให้เสร็จก่อนเพิ่มฟีเจอร์ใหม่ (ข้อ 1–7 ในหัวข้อ 8) ซึ่งตรงกับ Milestone 1 ใน [แผนแม่บท](02-master-plan.md)
2. รันระบบจริงหนึ่งรอบในเบราว์เซอร์และบนอุปกรณ์จริงก่อนงานอื่น เพราะเป็นช่องว่างของหลักฐานที่ใหญ่ที่สุด
3. ตัดสินใจ 4 เรื่องในหัวข้อ 9 ให้จบ
4. ปรับปรุงหรือลบเอกสารเก่า เพื่อไม่ให้คนและ AI อ้างอิงผิด
5. ทำการสำรวจตลาดและผู้ใช้แยกต่างหาก ก่อนจัดลำดับฟีเจอร์เชิงธุรกิจใน Milestone 2 เป็นต้นไป
